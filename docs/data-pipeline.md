# Data pipeline design

Status: historical rainfall and temperature released; autonomous monthly Final rainfall updater implemented

## Why the pipeline crops remotely

The public CHIRPS v3 yearly NetCDF files are several gigabytes each, and individual global daily TIFFs are commonly tens of megabytes. A baseline build must not download the full global archive.

For the historical baseline, the pipeline reads the Madagascar window from the published daily Cloud-Optimized GeoTIFFs using HTTP range requests. The work is divided by year so failed years can be retried independently. Each yearly job emits compact partial statistics rather than retaining raw daily global data.

Recent rainfall uses the same Final RNL daily COGs, native grid, and baseline window. Only complete calendar months are published. Preliminary and unfinished months are excluded.

## Historical bootstrap

1. Run one job for each year from 1991 through 2020.
2. For each daily Final RNL COG, read only the Madagascar bounding window plus a one-cell buffer.
3. Reject missing days, unexpected transforms, changed resolution, negative rainfall other than declared no-data values, and duplicate dates.
4. Maintain monthly totals, rainy-day counts, heavy-rain-day counts, wet-day rainfall sums and counts, and dry-spell state for every grid cell.
5. Emit a compact yearly partial result.
6. Merge all complete years into the 1991–2020 climate normal.
7. Apply the Madagascar land mask.
8. Generate 1 degree publication tiles with halos.
9. Validate sample locations and publish an immutable candidate baseline.

The build must be resumable. Completed years are content-addressed and do not rerun unless the source or methodology version changes.

## Temperature bootstrap

The pipeline requests ERA5-Land post-processed daily minimum and maximum 2 m temperature from the Copernicus Climate Data Store. Requests are cropped to the Madagascar bounding box. CDS cost limits reject a five-year daily-statistics request at this extent, so the historical bootstrap uses one complete year per request. Daily statistics use Madagascar local time, UTC+03:00.

CDS requests are asynchronous. The submission workflow records each request ID and exits rather than occupying a GitHub runner while CDS queues the work. After CDS reports success, the recovery workflow reopens those request IDs, downloads minimum and maximum independently, validates the paired grids, and emits a reduced yearly partial. A GitHub timeout therefore cannot discard a completed CDS job.

Thirty complete yearly partials are merged into the 1991-2020 temperature normal. Raw NetCDF files remain temporary artifacts; the normal retains only monthly mean daily minima and monthly mean daily maxima on the native 0.1 degree grid.

The exact authenticated request generated by the CDS download form must be compared with `pipeline/sources.py` before the first production retrieval. CDS occasionally changes request field names; pretending APIs are scripture has historically gone poorly.

## Current update

1. Inspect dated Final RNL source listings for complete months, including year-boundary coverage.
2. Select the latest twelve consecutive complete calendar months. Reject gaps or a regressed data-through date.
3. Restore checksummed monthly reductions from `chirps-monthly-v1`; acquire only missing months using HTTP window reads.
4. Verify the native grid, land mask, every daily observation, plausible rainfall, and integer day counts.
5. Upload each completed monthly NPZ plus JSON provenance and checksum as a verified ZIP before continuing.
6. Produce immutable content-addressed tiles and a matching manifest/health endpoint. Preserve both 1991–2020 baselines.
7. Preserve a full publication snapshot, run tests, deploy staging, and smoke-test three contrasting locations.
8. Commit verified data, deploy production, and verify the live manifest and tiles. Reruns compare the live release too, allowing a failed production deployment to recover even after its data commit succeeded.

The weekly check publishes only when new complete Final data arrive. Final normally follows in the third week of the next month; the freshness alert allows through the 27th. A failure or overdue source opens a deduplicated GitHub issue. Already archived Final months are reused; an upstream revision requires an explicit versioned rebuild rather than silently changing the historical reference.

## Release invariants

- Baseline tiles never change in place.
- A methodology change creates a new baseline version.
- Current releases identify their latest complete observation month and Final-only source.
- Tile-edge queries return the same result as an equivalent query before tiling.
- Raw downloaded rasters are temporary and are not committed to Git.
- Failed builds leave the active manifest untouched.
